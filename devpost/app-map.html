UndoTable — app map

A map of the finished code. Snapshot of commit b8cce33; later changes can make it drift.

What the app does

You photograph an object after each part you take off. UndoTable lines each photo up with the previous one, boxes what disappeared and remembers the part. Later it walks the steps in reverse, and a photo of a loose part tells you which step it came from. Everything runs in the browser; photos stay in IndexedDB on the device.

  • Page — index.html, styles.css, src/app.js: screens, buttons, box drawing.
  • Engine — src/engine.js: loads OpenCV.js and Transformers.js, runs compare and lookup.
  • Comparer — src/vision.js: align photos, find changes, cut a part out of its background.
  • Matcher — src/embed.js, src/match.js: image vectors and the sure / not sure / no close match decision.
  • Keeper — src/store.js: IndexedDB.

One action: “Where does this go?”

Reference route (not yet toured)

  1. The button. src/app.js, search async function runLookup. It takes the photo file, calls lookup with the stored parts and hands the result to showMatch.
  2. Turning a photo into a comparison. src/engine.js, search export async function lookup. It cuts the part out of its background (cutOut, using foreground in src/vision.js), makes DINOv2 vectors of the cut-out and the whole photo, and takes a colour signature.
  3. The decision. src/match.js, search export function rank. It scores every stored part, adds 0.1 × colour similarity, and returns sure, unsure (top two within 0.03) or none (best score under 0.5). showMatch in src/app.js shows one step for sure and two otherwise.
The verdict lines in rank 
  let verdict = 'sure';
  if (!scored.length || scored[0].score < floor) verdict = 'none';
  else if (scored.length > 1 && scored[0].score - scored[1].score < margin) verdict = 'unsure';
  return { ranked: scored, verdict };

From src/match.js; scored is sorted best first.

To change this, start here

  • How sure the app must be before it gives one answer — margin and floor defaults of rank in src/match.js.
  • The words shown on the lookup sheet — showMatch in src/app.js.
  • How small a change still gets a box — PASSES and the minArea default in src/vision.js.
  • Suggested part names — data/vocab.json, rebuilt with tools/build-vocab.mjs.
  • The sample teardown — samples/fan/manifest.json.

A practice to reuse

Decide with a measured test set, and keep part of it back. The open question “which model matches loose parts?” (prd.md > Open Questions) was settled by generating step-by-step teardown photos, running tests/harness/eval.mjs over 48 settings on two sets, and only then running the chosen setting once on a third set made afterwards. The numbers are in tests/photos/RESULTS.md: the held-out remote showed lower confidence than the sets used for tuning, which a single tuned set would have hidden.

On another project with a fuzzy “is it good enough?” question, write the score down first, tune on some examples, and check on ones you did not tune on.
